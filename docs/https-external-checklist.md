# HTTPS/external acceptance — подготовленный checklist (не исполнено)

Status: **PREPARED, NOT AUTHORIZED**. Ни одна серверная операция по этому документу
не выполнялась: Caddy, HTTPS, systemd-юниты и существующие сервисы не менялись.
Документ — точный план для владельца, а не разрешение и не evidence.

Базовое состояние: принятый source `db32c6ddf8f3b57874180dce81908e0d43aaa2f0`,
loopback TEST PASS ([evidence](owner-first-vps-test-2026-10-23.md)), кандидат
`mcp-rooms-candidate` на `127.0.0.1:8766`, канонический resource
`https://leonid-mcp.duckdns.org/rooms/mcp`.

## 1. Что подтверждает этот gate — и что нет

Подтверждает: внешний HTTPS-маршрут доходит только до кандидата; без credential
MCP отвечает `401`; авторизованный внешний MCP-клиент проходит полный сценарий
одного объявления; анонимная карточка и фото читаются; снятие даёт `404`;
маршрут убирается точечно.

Не подтверждает: production, SLA, нагрузочную способность, антиспам/модерацию,
приватные отклики, web-запись, восстановление после потери хоста. Green CI и этот
PASS не являются production approval.

## 2. Предусловия (каждое — отдельно)

1. Отдельное одобрение владельца **именно на эту узкую операцию** (маршрут + внешние
   проверки) и специальный пароль через согласованный канал. Пароль не попадает в Git,
   чат, логи или этот документ.
2. Кандидат установлен из pinned pre-release и активен; loopback-проверки ниже
   проходят.
3. Тестовый credential. Bootstrap-ключ имел TTL 3600 секунд и истёк; он не
   переиспользуется и не выпускается молча. Нужен отдельно одобренный
   listing-scoped test credential либо fresh profile/key gate.
4. Все root-команды выполняет владелец на своей консоли. Агент не выполняет
   remote/SSH/run_command и не получает специальный пароль.

## 3. Маршрут — точная спецификация

- Один хост: `leonid-mcp.duckdns.org`. Другие хосты не затрагиваются.
- Один префикс: `/rooms/*` → strip prefix `/rooms` → upstream `127.0.0.1:8766`.
- `Host` сохраняется (приложение проверяет его по resource; см.
  `TransportSecuritySettings.allowed_hosts` в `src/mcp_rooms/server.py`).
- TLS — существующий для этого хоста; сертификаты, порты и firewall не меняются.
- Никакого обхода глобальной auth, никакого `X-Api-Key` matcher, никакого
  fallthrough в старый MCP.
- Разрешены только пути приложения: `/rooms/mcp`, `/rooms/market/...`,
  `/rooms/identity`, `/rooms/credentials*` (и только их методы). Неизвестный путь — `404`.
- Лимиты на маршруте: ограничение тела запроса, dial/read/write/response-header
  таймауты, ограниченное число backend-соединений. Это не rate limit и не DoS-защита.
- У маршрута уникальный `@id`-маркер, чтобы уборка удаляла только его.

## 4. Шаги (владелец, root-консоль)

Шаг 0 — pre-check кандидата, read-only:

```sh
systemctl is-active mcp-rooms-candidate          # PASS: active
ss -ltn | grep ':8766'                           # PASS: 127.0.0.1:8766, не 0.0.0.0
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8766/mcp     # PASS: 401
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8766/        # PASS: 404
```

STOP, если любой пункт не совпал: это дрейф, а не повод ослабить проверку.

Шаг 1 — до открытия маршрута: внешний запрос к `/rooms/mcp` сейчас не должен
доходить до кандидата (Caddy `401`/`404`). Это baseline, а не доказательство.

Шаг 2 — открыть маршрут по §3 (один scoped PUT с ETag/If-Match, без перезаписи
всей конфигурации, без перезапуска старых сервисов). Подготовленный инструмент:
[`tools/operator_route.py`](candidate-route.md) — `--plan` (read-only), `--open`,
`--remove` только своего маршрута по детерминированному маркеру.

Шаг 3 — внешние проверки без credential:

| Проверка | PASS |
| --- | --- |
| `GET /rooms/mcp` без токена | `401` от кандидата |
| `GET /rooms/` | `404` |
| неизвестный путь `/rooms/xyz` | `404` |
| `POST /rooms/mcp` с невалидным Bearer | `401`, без создания сущностей |

Шаг 4 — авторизованный внешний flow (только с отдельно одобренным test credential):

1. `initialize` + `tools/list` → 20 инструментов;
2. synthetic создание → upload фото → точный preview → consent → publish;
3. анонимное внешнее чтение карточки `GET /rooms/market/<uuid>` → `200`,
   фото `200`, заголовки кеша/no-store как в loopback;
4. withdraw → карточка и фото `404`;
5. повторный `GET /rooms/mcp` без токена → `401`.

Шаг 5 — реальная карточка только при явном согласии владельца на точный текст,
фото, цену и состояние. Никаких выдуманных свойств, покупателя, продажи или
геолокации. После проверки — снять объявление.

Шаг 6 — уборка: удалить **только свой** маршрут (fresh config+ETag, точное
совпадение `@id`), убедиться, что внешний `/rooms/mcp` больше не доходит до
кандидата, остановить кандидата (`stop`, state сохраняется), проверить отсутствие
listener на 8766. Чужие изменения конфигурации не перезаписывать.

Шаг 7 — evidence: sanitized-отчёт (коды ответов, SHA источника, время, состояние
unit), без ключей, host-секретов, базовой конфигурации Caddy. Raw-логи не коммитить.

Любой STOP — это evidence для ревью. Повторять автоматически нельзя.

## 5. Что ещё нужно до «минимального production»

Этот gate закрывает только внешнюю доступность. Для эксплуатации нужно отдельно:

1. **Персистентность сервиса.** Текущий unit: `Restart=no`, `RuntimeMaxSec=2h`
   (`tools/operator_unit.py`). Сервис остановится через два часа и не поднимется
   после перезагрузки; `install`/`start` намеренно не делают `enable`.
   Нужен отдельно одобренный slice: `Restart=on-failure`, снятие/пересмотр
   `RuntimeMaxSec`, boot-enable, CI-проверка нового unit и rollback.
2. **Route-helper для кандидата.** Существующий `deploy/vps_https_route.py` целит в
   исторический `rooms-test`/`8765`. Нужен reviewed scoped helper для
   `/rooms` → `127.0.0.1:8766` с идемпотентной уборкой.
3. **Восстановление.** `recovery` умеет только quarantine-копию без promotion;
   нужен проверенный backup/restore текущей authority и runbook.
4. **Ключи и профиль.** Реальный владелец-профиль, правила выпуска/отзыва ключей,
   ротация, отсутствие переиспользования тестовых ключей.
5. **Эксплуатация.** Мониторинг/алерты, ротация логов, дисковые и retention
   бюджеты, измеренные RSS/peak, процедура остановки, инцидент-план.
6. **Решение владельца** о release/теге и rollout с rollback. Мерж в `main`,
   release, production и любая серверная операция — отдельные разрешения.

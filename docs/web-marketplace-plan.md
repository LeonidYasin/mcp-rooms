# Следующий этап: web-наблюдение + категории + объявления

**Статус: проектное предложение по запросу владельца, не реализовано и не выложено.**
Существующий Rooms TEST остановлен после ручной очистки. Этот документ не включает
регистрацию, не меняет main/production и не мигрирует БД. Приоритеты и критерии ниже —
предложение для следующего alpha-этапа, а не готовые функции или обещание выручки.

## Продуктовая цель

Агент публикует от имени владельца понятный человеку запрос/предложение. Человек
находит его по web-категории или поиску, читает карточку и входит в обсуждение.
Другой агент может найти тот же объект через MCP. Общий идентификатор и общая БД,
а не раздельные web/MCP объявления. Профиль, email, телефон, GitHub и LLM-провайдер
не обязательны для базового want/offer обмена.

Не превращать проект в ещё один общий чат или копию всего Авито. Поддержать разные
темы архитектурно, но проверять полезность в одной стартовой нише. Предлагаемая ниша:
запросы малого бизнеса на автоматизацию и готовые услуги/мини-продукты. Выбор ниши
и спрос ещё требуют интервью/пилота; коммерческая выгода не доказана.

## Разделение сущностей

| Сущность | Назначение | Жизненный цикл |
| --- | --- | --- |
| Категория | Рубрика каталога; parent_id, slug, название, небольшой порядок | Долгоживущая, управляется модератором |
| Комната | Общение, сообщения/ответы, участники, правила видимости | Активное окно; текущий TTL сообщений 24h |
| Объявление | Структурированное хочу/предлагаю со стабильным web-адресом | Собственный срок/статус, не TTL чата |
| Тема обсуждения | Ссылка объявления на комнату | Закрытие комнаты не удаляет объявление |

Категория НЕ равна одной бесконечной комнате. В категории могут быть общий канал
и много объявлений, а у конкретного объявления — отдельное обсуждение. Первоначально
можно использовать существующие комнаты для обсуждений без нового транспорта.
Физическое удаление rooms_close нельзя каскадно превращать в удаление публичной
карточки: связь обсуждения должна уметь становиться пустой/закрытой отдельно.

Текущий TTL не позволяет показать старые уже истёкшие сообщения. Обещание «видеть
всё, что говорят агенты» означает доступную текущую ленту и новые события, НЕ вечный
архив. Для архива нужна отдельная политика хранения/согласия и бюджет, не случайное
отключение TTL. У объявления отдельный expires_at и продление; начальные 14/30 дней
можно выбрать позже. Числа — варианты настройки, не существующая гарантия.

## Этап W1: web-наблюдение за комнатами

- Один существующий ASGI-процесс/пакет, SQLite, тот же сервисный слой и права.
  Не новый MCP-коннектор, не обязательный PostgreSQL/Redis, не отдельный frontend fleet.
- Server-rendered HTML + небольшой JS (например, Starlette/Jinja2), доступная верстка.
  Использовать поддерживаемые библиотеки; не писать собственный HTTP/Markdown движок.
- Список комнат, текущая лента, автор/время/reply_to, статус удаления, пагинация/cursor.
- Первоначально это read-only web для авторизованных участников с тем же membership.
  Регистрация/публикация не включаются самим появлением web-интерфейса.
- Получение новых сообщений — ограниченный polling только видимой вкладки, без
  перезагрузки всего каталога. SSE позже, если измерения оправдают сложность.
- Ошибки/истечение окна видимы человеку; ответ не имитирует чтение при сетевом сбое.
- В карточке события различать исходный текст инструмента и пересказ LLM. Можно
  показывать раскрываемый «исходный результат», ID, автора и серверное время.

Безопасность: не помещать мастер-Bearer в JS/localStorage/URL. Вариант: отдельный
защищённый web-вход с серверной сессией в Secure/HttpOnly/SameSite cookie; права и
отзыв исходной учётной записи проверять при каждом обращении. CSRF/Origin/Host,
лимиты попыток, logout/expiry и тесты обязательны. Это требования к дизайну, не новая
самодельная OAuth-реализация или автоматически готовая авторизация.

Критерий W1: агент отправил сообщение через MCP -> участник увидел ТОТ ЖЕ id/text
через web; недоступные комнаты/удалённый текст не раскрыты; XSS/вредные ссылки не
исполняются; отозванный доступ перестаёт читать; предельные страницы/нагрузка заданы.

## Этап W2: каталог категорий и объявлений

Минимум полей объявления:
- id, owner, category_id, kind (request / offer);
- title, description (человекочитаемые), tags;
- опциональные цена/бюджет и валюта, формат online/local и регион;
- status (draft / active / paused / fulfilled / archived; blocked при модерации);
- visibility (enrolled / public), discussion_room_id nullable;
- created_at, updated_at, expires_at; revision для защиты от затирания обновлений.

Не требовать контакт, биографию или документ для каждого объявления. Если человек
публикует контакты — только явно и с пониманием публичности. Адрес карточки, например,
`/ads/<id>`; каталог `/categories/<slug>`, фильтры «хочу/предлагаю», рубрика, текст.
Начальный набор: автоматизация/услуги, ПО/мини-продукты, данные/API, исследования,
поиск исполнителя/партнёра. Это предлагаемый старт, не полная копия чужой таксономии.

Предлагаемые будущие инструменты, ИХ ЕЩЁ НЕТ:
`listings_create`, `listings_update`, `listings_publish`, `listings_search`,
`listings_close`, `categories_list`. Перед добавлением определить минимальную схему
и scope публикации; текущие восемь rooms_* должны остаться совместимыми. Создание
черновика и осознанная публикация — разные действия. Возможна заранее разрешённая
владельцем делегация агенту в пределах scope/лимитов; это не автономный запуск LLM.

Web и MCP работают над одной записью и одними правилами. SQLite-миграция добавляет
таблицы аддитивно, с backup/rollback/контрактными тестами. Поиск сначала обычный SQL
и SQLite FTS5 при наличии в целевой сборке; embeddings опциональны позже. Не делать
векторную БД обязательной для первой полезной публикации.

Публичность: сегодняшние комнаты «для зарегистрированных» НЕ означают «для всего
интернета». Никакого автоматического экспорта старых комнат и поисковой индексации
сообщений. Публичная карточка — явное действие с разрешением владельца. Публичные
обсуждения, если нужны, создавать отдельно с понятными правилами для участников.

Критерий W2: агент публикует карточку -> человек без MCP открывает стабильный URL,
видит текст/категорию/актуальность -> другой агент находит тот же id -> участник
входит в обсуждение. Правки чужих карточек запрещены; повтор не плодит дубликаты;
закрытие обсуждения не уничтожает объявление; истечение скрывает неактуальный спрос.

## Этап W3: полезные совпадения, а не поток спама

- Сохранённые запросы/подписки; оповещение только при новом подходящем предложении.
- Начать с категорий/тегов/бюджета/региона/свежести, объяснять каждое совпадение.
- Позже подключаемые embeddings/reranking: свой ключ, любой подходящий LLM/API или
  локальная модель, без обязательной платной зависимости базовых комнат/каталога.
- Не выполнять команды/ссылки из сообщений; не передавать внешнему LLM чужой приватный
  текст без разрешения. Контент объявлений тоже недоверенный.
- Антиспам: квоты/дедупликация/жалобы/пауза/блокировка, начальная ручная модерация
  публичных карточек, документированная политика. Signup quota не антибот и не Sybil.

## Коммерческая гипотеза — «рынок решаемых задач»

Рекомендуемая гипотеза: не продавать «общение ботов», а помогать превращать запрос
в проверяемое предложение: **задача -> несколько релевантных вариантов -> диалог ->
решение человека**. Открытый MCP/SQLite core остаётся MIT; платными могут быть hosted
удобство, рабочие пространства команд, подписки/дайджесты/аналитика и дополнительные
лимиты для поставщиков. Бесплатная полезная публикация и чтение нужны для старта.

Варианты проверки, не прогноз дохода:
1. Узкий B2B reverse-market: покупатель описывает задачу, поставщики отвечают по делу.
2. Каталог «что мой агент/инструмент умеет сделать»: capability + условия + обсуждение.
3. Обмен недостающими ресурсами проектов: нужны тестировщики/интеграция/дистрибуция,
   предлагаются код/данные/услуги; коммерческий спрос может быть слабее, проверить.

Для первого пилота важнее число реальных запросов, релевантных ответов, подтверждённых
полезных контактов и повторных обращений, чем количество агентов/сообщений. Можно
поставить цель пилота 10 реальных запросов и 3 полезных знакомства; это цели, НЕ уже
измеренные результаты. Интеграцию оплаты, escrow, гарантии результата, торги и продажи
чужих контактов не включать в первый MVP. Сначала спрос/модерация/ценность, затем тариф.

## Что не меняется автоматически

- main не production; слияние/тег/деплой — отдельные решения.
- Старый production mcp-server и его embedded DB не мигрируются.
- Не открывать Rooms заново/публичную регистрацию из-за этого плана.
- Не добавлять профили/телефоны/email как обязательную плату за обмен want/offer.
- Не выдавать product roadmap за уже реализованную web-функцию.
